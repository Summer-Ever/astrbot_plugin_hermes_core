# astrbot_plugin_hermes_core

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![AstrBot](https://img.shields.io/badge/For-AstrBot-blue)](https://github.com/AstrBotDevs/AstrBot)

复刻 [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) 学习闭环的 AstrBot 插件：让 AstrBot 的 bot 越用越懂你、能力越用越强，而不替换 AstrBot 任何原生功能。

## 功能对照（vs Hermes）

| Hermes 能力 | 本插件实现 |
|---|---|
| SQLite + WAL + FTS5 会话存储 | `modules/db.py`；检索不依赖 FTS 分词，改用字符二元组打分（见下节） |
| 长期记忆注入（MEMORY.md/USER.md） | 三层注入：「关于你」常驻块 + 按当前消息检索 top-k + 相关历史，经 `extra_user_content_parts` 临时注入（保护 prompt 缓存） |
| 周期性记忆 nudge / LLM 总结 | 后台循环调用你已配置的 Provider，把新对话压缩为记忆条目（JSON 协议） |
| 技能自动生成（Markdown Skill） | 总结时一并提炼技能；模型也可通过 `save_skill` 工具主动沉淀，同名自动更新 |
| 工具化记忆检索 | 6 个 llm_tool：`search_memory` / `save_memory` / `list_skills` / `read_skill` / `save_skill` / `update_skill` |
| （本插件扩展）WebUI 管理页面 | AstrBot 侧边栏出现「记忆与技能」页面：概览/记忆/技能/模型/设置/工具，可视化检索、编辑、合并记忆与技能，管理总结模型链 |
| （本插件扩展）多用户隔离 | 记忆与技能按 `用户 > 群 > 全局` 三级作用域存储与召回，群聊中不同群友互不污染 |
| （本插件扩展）接管 AstrBot 记忆 | 原生对话历史一键导入 + 内置记忆/其他记忆插件冲突检测 |

## 数据维护（v0.12.1）

后台循环每天自动做一次维护（`retention_days` 控制，默认 90 天，`0` 关闭）：

- 原始消息按保留期批量清理并同步全文索引，随后收缩 WAL——**只删已经总结过（水位之前）的原文**，没进记忆的部分不会被删掉；记忆/技能/身份任何情况下不参与清理
- 升级遗留的一次性垃圾（如 v0.12 移除渲染模块后的 `renderer/`、`renders/` 目录）在首次运行时自动清除，只清硬编码白名单目录，且删除前校验 realpath 必须仍位于插件 data 目录内

## 记忆隔离：群聊多人使用不串味

Hermes 本身是单用户私人助理，没有多用户概念；本插件为此增加了作用域层：

- `memory_scope=user`（默认）：记忆归属到具体发言人，召回时按 **本人 → 本群公共 → 全局** 优先级排序；群友 A 的偏好不会注入给群友 B
- `memory_scope=group`：以群/会话为单位共享记忆，适合"群规、群项目"这类公共知识
- `memory_scope=global`：全机器人共享（等同旧版行为，不建议群聊开启）
- `per_user_history=true`（默认）：历史检索增加 `sender_id` 过滤，不会把同群其他人的对话当上下文注入
- 技能库全机器人共享——技能是"能力"而非隐私，这也是 Hermes 的设计
- 总结器会收到带 `[用户 ID(昵称)]` 标记的对话，产出记忆时自动归属到对应人；归属不明的降级为群公共记忆

### 关于 ID：QQ 官方机器人没有"QQ 号"

这点必须说清楚，否则会踩坑。AstrBot 的 QQ 官方适配器（`qq_official`）里：

| 场景 | `get_sender_id()` | `get_group_id()` | 会话 umo 第三段 |
|---|---|---|---|
| 群消息 | `member_openid`（群内成员 openid） | `group_openid` | `group_openid` |
| C2C 私聊 | `user_openid` | 空 | `user_openid` |

- `member_openid` **按群维度不同**：同一个人在群 A 和群 B 是两套 ID
- `member_openid` ≠ `user_openid`：同一个人在群聊和私聊是两套 ID
- openid **与机器人 AppID 绑定**：换 bot 后全部 ID 变化

因此本插件做了两件事：

1. **群公共记忆的键用 `(platform, group_openid)`，不用 umo** —— 所以开关 `unique_session`（会改写 umo 为 `sender_group`）不会让既有群记忆失联
2. **身份别名表**：`/hermes 绑定 <另一个ID>` 可把一个人的多个 openid 归一，跨群/跨私聊的记忆合并

> 用 `NapCat/aiocqhttp` 系列适配器时 `sender_id` 就是真实 QQ 号，上面的碎片化问题不存在。

## 接管 AstrBot 的记忆体系

本插件在 `on_llm_request` / `on_llm_response` 两个官方钩子上完成"注入 + 落库"，因此可以把 AstrBot 的记忆职责完全收拢过来：

1. **关闭其他记忆来源**（避免双重注入）：WebUI 停用其他记忆类插件（如 livingmemory、hindsight 等）；若你的版本内置了试验性长期记忆，在 配置 → AI 相关选项 中关闭
2. **导入原生历史**：在需要的会话里执行 `/hermes 导入历史`，把 AstrBot 原有对话记录并入本插件记忆库，切换无感
3. **冲突自检**：`exclusive_memory=true`（默认）时，插件启动会在日志里列出检测到的其他记忆插件并提醒
4. **统一管理入口**：此后记忆的查看、删除、导出、总结、技能全部走 `/hermes` 命令组

## 安装

方式一（推荐）：AstrBot WebUI → 插件管理 → 从仓库安装，填入本仓库地址。

方式二（手动）：

```bash
cd AstrBot/data/plugins/
git clone https://github.com/Summer-Ever/astrbot_plugin_hermes_core.git
```

然后在 WebUI → 插件管理 → 重载，并确保已配置至少一个 LLM Provider（总结功能复用它）。

## 命令

- `/hermes 状态` — 记忆/技能/消息统计（含已合并条数）
- `/hermes 总结` — 立即触发一次总结
- `/hermes 整理` — 把碎片化的相似记忆合并成一条；`深度` 全量交给模型归纳（可清理垃圾条目）、`预览` 只看不写、`重来` 忽略上次断点。深度整理也会按作用域攒够 200 条时自动在后台触发，见「自动深度整理」一节
- `/hermes 整理结果` — 查最近一次整理的产出与进度（整理在后台跑，结果会主动推送）
- `/hermes 技能整理` — 把重复的技能合并成一个；加 `预览` 只看不写（管理员）
- `/hermes 记住 <内容>` — 手动写入记忆
- `/hermes 记忆` — 查看最近记忆（含 id，可配合删除）；**非管理员只看得到自己的**
- `/hermes 忘记 <id>` — 删除某条记忆；**只能删自己的**（管理员可删任意）
- `/hermes 技能` — 列出技能；`/hermes 技能 <名称>` 查看全文
- `/hermes 导出` — 导出 MEMORY.md 到插件数据目录（管理员）
- `/hermes 导入历史` — 导入 AstrBot 原生对话历史（接管记忆时用）
- `/hermes 我的ID` — 查看当前平台的 sender_id / 归属 ID / 群 ID / umo（排查隔离问题）
- `/hermes 绑定 <ID>` — 把一个别名 ID 归并到当前身份（跨群、跨私聊合并记忆）；已绑定给别人、或对方在本机说过话时，需要管理员
- `/hermes 身份` — 查看所有身份绑定（管理员）；`/hermes 解绑 <ID>` 只能解自己名下的
- `/hermes 清空记录` — 清空对话上下文但**保留记忆与技能**：先预演条数，再加 `全群 确认`（管理员，会同时清 AstrBot 原生会话）或 `我 确认`（仅自己的消息记录）

> `/hermes 总结`、`/hermes 整理`、`/hermes 技能整理` 会读写**所有人的**对话与记忆，均要求管理员。
> 权限判断拿不到明确结果时按「不是管理员」处理（fail-closed），不会因为适配器版本差异放开。

## 总结是怎么触发的（按会话独立）

三个参数容易误解，实际规则是**按会话独立判断**（会话 = 一个群窗口，或一个私聊窗口）：

| 参数 | 真正的含义 | 不是 |
|---|---|---|
| `summarize_interval_minutes` | 每 N 分钟醒一次，**逐个会话**检查 | 不是「每 N 分钟总结一次」 |
| `min_new_messages` | **单个会话**攒够这么多条才总结 | 不是「全库合计够 N 条」 |
| `summarize_grace_hours` | 某会话的消息超过 N 小时还没总结，即使不够条数也强制总结 | 不是时效性要求 |

举例（阈值 8 条 / 兜底 6 小时）：

- 群 A 攒了 10 条 → 总结群 A，一次 LLM 调用
- 群 B 只有 3 条但已经放了 7 小时 → 兜底总结群 B
- 私聊 C 刚聊 2 条 → 跳过，等下轮继续攒或等兜底

**每个会话独立一次 LLM 调用、串行执行，绝不把多个会话塞进同一个 prompt**；各会话的总结水位（`meta` 表 `summarized:<会话ID>`）互不影响。

一个必须说清的点：**会话不等于人**。同一个群里的 A 和 B 共享一个会话，他们的话会进同一次总结——这是刻意的，因为群聊本来就是多人交织的对话，按人拆开会丢失「谁在回谁」的上下文，而且 LLM 调用次数会翻倍。归属安全靠三层保证：每句带 `[用户ID(昵称)]` 标记 → 模型产出 `owner` 字段 → 写入前校验 owner 必须出现在本批对话的 ID 里，否则降级为群公共记忆（不会硬塞给某个人）。

如果确实要求「完全按人隔离总结」，把 AstrBot 的 `unique_session` 打开即可：群里每个人变成独立会话，自然就按人拆开了（代价是失去群公共上下文）。

## 记忆会自己整理（v0.6.0）

不做整理的话，「喜欢吃香蕉」和「喜欢吃苹果」会变成两条八竿子打不着的记忆，
用的时候模型只捞到一条；技能更糟——同一个绘图能力被总结三次，就变成三个技能，
每次用之前都得读一遍。

整理要花一次模型调用，所以**不逐条整理**，而是先排队、攒够阈值再一次性处理
（详见下面的「什么时候整理」）。

攒够之后会自动跑一次**巩固**：

1. **本地找候选**：拿刚写的记忆和同一用户/同一群的历史记忆比字面相似度（字符二元组 Jaccard），
   只把相近的挑出来。没有候选就结束，不花钱。
2. **模型判断**：把候选组一次性交给 LLM，让它决定怎么合——
   - 互补的合并：`喜欢吃香蕉` + `喜欢吃苹果` → `喜欢吃香蕉、苹果`
   - 冲突的取最新：`喜欢猫` → 后来 `不喜欢猫了`，只留最新状态
   - 无关的保持分开，不硬凑

字面相似度**只用来召回**，不直接决定合并。原因很实在：`喜欢吃香蕉 / 喜欢吃苹果` 相似度只有 0.33，
而 `养了只猫叫咪咪 / 养了只狗叫旺财` 有 0.38——字面分不出该不该合，得靠模型读语义。

**整理一次是全库，但绝不跨人**：所有活跃记忆按「谁 + 哪个群 + 可见性」分桶，一个桶一次模型调用。
同一个人私聊说的私事（`private`）和群里说的偏好（`group`）是两个桶——并成一条就只能二选一：
要么私事被当成群里的公开信息念出来，要么群里的信息从此在群里消失（v0.12.13）。
桶内超过 `consolidate_chunk_size` 条再切片，所以「4 片」是切片数，不是用户数。

### 什么时候整理：攒够 N 条才合并（v0.6.1）

新记忆不会立刻合并，而是进一个**待整理队列**，等队列攒够阈值再一次性处理：

| 配置项 | 默认 | 含义 |
|---|---|---|
| `consolidate_every_n_memories` | 10 | 累计新增 10 条记忆才整理一次；`0` = 关闭自动，只能手动 `/hermes 整理` |
| `skill_consolidate_every_n` | 5 | 累计新增/更新 5 个技能才合并一次；`0` = 关闭自动，只能手动 `/hermes 技能整理` |

这样 100 条新记忆最多触发 10 次整理，而不是每次总结都多花一次调用。
队列里的 id 存在 `meta.consolidate_pending_memories`（上限 200 条，超出丢最旧的），
模型手动 `save_memory`、`/hermes 记住` 存的记忆也会进队列，不会漏掉。

`/hermes 状态` 里能看到进度：

```
自动整理: 记忆 3/10 条、技能 1/5 个 触发一次（每次约 1 次模型调用）
```

整理失败（模型超时、报错）时**不清队列**，下一轮自动重试；成功才清零。
手动执行 `/hermes 整理` / `/hermes 技能整理` 会顺手清空对应队列，避免重复整理。

### 自动深度整理：按作用域攒够 200 条（v0.12.22）

普通整理靠字面相似度找候选，**字面完全不重合的同义记忆永远配不上对**
（「客厅角落那台机器」vs「用户有一台群晖 NAS」的 bigram Jaccard 是 0）。
深度整理绕过聚类、把整批记忆交给模型归纳，本来只有手动 `/hermes 整理 深度`
能跑；现在它也能自动触发：

| 配置 | 默认 | 含义 |
|---|---|---|
| `consolidate_deep_every_n_memories` | 200 | 某个作用域自上次深度整理以来新增多少条**仍活跃的记忆**，才自动归纳一次；`0` = 关闭自动，只能手动 |

要点：

- **数的是记忆条数，不是聊天消息数。** 一次总结通常只产出 0~3 条记忆，
  攒到 200 条记忆往往对应上千条消息，节奏比直觉慢得多。
- **按作用域分别计数，跟 `memory_scope` 无关。** 分桶依据是记忆行自身的
  `owner_id / group_id / visibility / platform`（`_scope_bucket`），而
  `memory_scope` 只是读取侧的召回策略，不改变记忆归属。某个用户或某个群
  达标就只整理它自己，不会把全库其它桶拖着一起跑模型。
- **计数用「每桶水位 + 仍活跃」**，不是累计新增：普通整理合并掉的、
  手动深度整理压缩掉的记忆都会自然退出计数，不需要两套队列互相修正；
  钉住的条目不计入。水位存在 `meta.deep_consolidate_watermarks`。
- **在后台跑，不阻塞总结循环。** 深度整理逐片调模型、最长可到十几分钟，
  挂在总结路径里 await 会把下一轮总结和每日维护一起堵死。自动任务不覆盖
  手动整理的报告、不推消息、不动普通整理队列。
- **单次最多 3 个作用域。** 升级后第一次检查时所有桶都没有水位，可能同时
  达标；不限量会一轮打爆模型预算。没跑完的桶留到后面的轮次。
- **碎片化兜底**：所有桶都不到阈值、但全局累计达到 4 倍阈值时，挑条数
  最多的前 3 个桶整理，避免「20 个人各 10 条」永远触发不了。
- 深度整理默认 `consolidate_chunk_size=30`，200 条约切 7 片；分桶键与
  可见性一致，绝不跨用户/跨群/跨可见性归纳。

合并产物现在**必须保留各条原文用于指代同一事物的不同说法**（次要说法用
括号附在主要说法之后，整条尽量不超过 200 字）。原因是 `merge_memories`
会把旧条标成非活跃，检索只查活跃条目；如果合并时只留一种说法，另一种
问法的召回会从 1 条直接掉到 0 条——整理解决了重复，却制造了失忆。

技能的重复问题走另一条路：

- 总结前会把**已有技能清单**放进提示词，要求同类流程直接沿用已有技能名，不要另起新名（从源头减少重复）
- 同名技能不再直接覆盖，而是**先读旧版再合并**，保留旧版里仍有效的步骤
- `/hermes 技能整理` 把名字/触发条件相近的多个技能合并成一个，`预览` 可先看计划

**误合并能回滚**：合并后旧条不删除，只把 `merged_into` 指向新条，检索时排除。真合错了，
直接把 `merged_into` 置回 0 就能恢复（也保留完整历史，方便排查）。

## WebUI 管理页面（v0.7.0）

装好后，AstrBot WebUI 的侧边栏会出现插件页面 **「Hermes · 记忆与技能」**（插件详情里也有入口）。
页面零依赖（无 CDN、无构建），样式跟随面板明暗主题，共六个标签：

| 标签 | 能做什么 |
|---|---|
| **概览** | 消息/记忆/技能统计、数据库大小、总结模型、整理队列进度条、最近记忆与技能使用 Top |
| **记忆** | 关键词/作用域/类型筛选 + 分页；编辑、删除、新增；勾选多条**手动合并**（可改写合并文案）；勾选「显示已合并」查看历史 |
| **技能** | 左列表右编辑器；查看/修改技能名、触发条件与 Markdown 正文，支持**渲染预览**；新建/删除 |
| **模型** | 总结用的模型链：主模型 + 有序降级链、容错策略、连通性测试、调用日志（详见下一节） |
| **设置** | 直接编辑插件配置（与 AstrBot 配置页同一份文件），schema 驱动的表单，bool 开关/下拉/数值/文本各自呈现；标「需重载」的项会提示 |
| **工具** | 立即总结、记忆整理（预览/执行）、技能整理（预览/执行）、导出 MEMORY.md、身份别名绑定 |

安全设计：

- 手动合并记忆要求选中条目同用户/同群，跨边界的合并会被后端直接拒绝
- 配置保存会按 schema 校验类型与取值范围，非法值不会写入
- 所有删除操作都有二次确认弹窗；记忆合并是软删除，可回溯

实现：页面在 `views/hermes/`，接口通过 `context.register_web_api` 注册（`webapi.py`），
前端经 AstrBot 的 plugin page bridge 调用，全部数据留在本机。

## 模型链：总结不必用对话模型（v0.8.0）

对话模型要求聪明、会玩工具；总结只需要「读得懂、写得准」。把总结绑死在对话模型上，
遇到笨模型、短上下文、或者临时抽风，后台总结就整批失败——而且没人看见。

「模型」标签解决这件事：

- **自动发现**：列出 AstrBot 里配置的全部对话模型（含上下文长度、启用状态、哪个是当前对话模型），不另存密钥
- **主模型 + 降级链**：主模型失败后按顺序尝试降级模型，支持上移/下移排序；可一键「一次性复制 AstrBot 对话配置」（只填进草稿，保存后才生效）
- **与主体设置解耦（v0.12.15）**：主模型与降级链只认插件自己的配置，**不跟随 AstrBot 主体的对话模型设置**。旧版在留空时会实时读「当前对话模型」，主体一换，后台总结跟着换——记忆是长期数据，模型换了归纳风格与成本都会无声漂移，事后没法归因。升级时若配置为空，会把当时的模型快照写进插件配置（只做一次），之后主体怎么改都无关；留空则插件不调用模型，命令会明确提示去「模型」页选
- **逐模型重试**：每个模型失败后按退避基数指数重试（`llm_max_retries`），整条链有总尝试上限，不会无限烧
- **错误分类**：超时/连接/限流/鉴权/上下文超长/服务端/空响应各有处理策略——鉴权错重试没有意义，直接换模型；**429/额度用尽一律不原地重试**，直接换模型并按 `Retry-After` 冷却
- **出站节流**（v0.12.10）：同一模型有最小调用间隔（`llm_min_interval`）与每分钟次数上限（`llm_rpm`），这是整理连续调用时不把自己打成 429 的关键
- **失败冷却**：连续失败的模型进入冷却期（鉴权错 4 倍、限流 3 倍且尊重 `Retry-After`），冷却状态跨重启保留；批处理场景下全部在冷却就直接收工，不再「宁可撞一下」白等一个超时
- **按上下文裁剪**：同一个 prompt 按目标模型的 `max_context_tokens` 动态截断，小上下文模型当降级模型也能接住；另有全局单次字符上限防止大模型吞整段历史烧钱
- **连通性测试**：对任意模型发一条极短请求，验证密钥/网络/额度，显示延迟和失败原因
- **调用日志**：最近 80 次调用的时间、用途、模型、尝试次数、耗时、结果与错误摘要；单模型成功率统计

所有总结、记忆整理、技能合并都走这条链（`modules/router.py`）；单个会话总结失败不拖累其他会话，
失败的那批消息下一轮自动重试。

## 整理怎么不触发风控、也不白等（v0.12.10）

整理是**连续调用**：一个用户一个作用域，一个作用域可能几十上百条记忆。
它和聊天不一样——聊天有自然的思考间隔，整理没有，所以最容易踩两个坑：
被限流打成 429，和模型不通时一路空等。

四条约束，缺一条都会出问题：

| 约束 | 为什么 | 怎么做的 |
|---|---|---|
| **切片** | 100 条记忆一次喂进去，prompt 长、出结果慢，一超时整批全丢 | 每片最多 `consolidate_chunk_size`（默认 30）条——**不是"总共分几片"，是按每个作用域的条数切**；大桶先跑 |
| **单片硬顶** | 3 个模型 × 3 次尝试 × 60 秒 = 540 秒，一片就能吃光整次预算 | `consolidate_unit_seconds`（默认 180 秒）：一片到点就放弃，继续下一片 |
| **总预算** | 片数多时可能无限拖 | `consolidate_budget_seconds`（默认 900 秒）到点就停，如实报告"跑到第几片" |
| **连续失败止损** | 模型链整体挂了还继续跑，只是把 429 撞得更狠 | 连续 `consolidate_max_fail_streak`（默认 2）片失败就停，文案说明原因 |
| **断点续跑** | 跑到一半被 kill，重发会从第一片重来，白烧 token | 每跑完一片记进 `meta.consolidate_checkpoint`；记忆内容没变就只补没跑的片，`/hermes 整理 深度 重来` 可强制从头 |

配套的两条链路行为：

- **节流**：同一模型两次调用至少间隔 `llm_min_interval`（默认 1.5 秒），每分钟最多 `llm_rpm`（默认 10 次）。
  配额快满时**不会干等**——剩余预算不够就直接停下，留给下一次整理。
- **429 不重试**：识别到限流立刻换下一个模型，并按 `Retry-After`（HTTP 头或正文里的 "try again in 12s"）冷却该模型，
  冷却时长 = max(3 倍基础冷却, Retry-After)。冷却状态写进 meta，重启不会再去撞同一个坏模型。
- **冷却有硬下限**：限流 ≥120 秒、超时 ≥90 秒、鉴权 ≥300 秒。把 `llm_cooldown_seconds` 调成 5 秒
  等于每片都把坏模型重新撞一遍，所以这几个下限不受配置影响。

实测（同一份 prompt：40 条记忆 ≈ 2.1k 字，走 AstrBot 的 provider 通道）：

| 模型 | 短提示 | 长提示 |
|---|---|---|
| `deepseek/deepseek-flash` | 0.7 秒 | **9.5 秒** |
| `openai/qwen3.7-flash` | 2.3 秒 | **32.5 秒** |
| `openrouter/nvidia/nemotron-3.5-super-vl:free` | 1.9 秒 | **51.9 秒** |
| `zhipu/glm-4.7-flash` | 超时 | 超时（429 风暴） |

结论：**30 秒超时等于只允许主模型成功**，降级模型全部被当成"不通"。
同时 AstrBot 的 provider 默认在内部重试 5 次（指数退避，单次最长等 30 秒），
一次 429 会变成 1-2 分钟静默等待，外层只能看到"超时"——所以插件调用统一传
`request_max_retries=1`，退避与换模型全部由本层负责。

| | 改造前 | 改造后 |
|---|---|---|
| 单次调用超时 | 30 秒 | **60 秒** |
| AstrBot 内部重试 | 5 次（静默，最长几分钟） | **1 次**，由本插件决定重试 |
| 单片硬顶 | 90 秒 | **180 秒** |
| 每片条数 | 40 | **30**（生成更短更快） |
| 429 之后 | 内部重试到超时 | **立即换模型** + 冷却 180 秒起 |

## 技能双域：个人技能 vs 本体技能（v0.9.0）

AstrBot 本体有一套技能目录（`data/skills/<slug>/SKILL.md`，全局共享、常带 `scripts/`），
插件自己也沉淀技能。两边都叫「技能」，于是在聊天里说“帮我改一下 xx 技能”时，
模型往往跑去改本体那份文件——改的是全局文件，而且会波及所有人。

从 v0.9.0 起按域切开，写权限严格分层：

| | 个人技能（Personal） | 系统技能（System） |
|---|---|---|
| 存放 | 插件 SQLite，按 `(owner_id, name)` 唯一 | 本体 `data/skills/` |
| 可见 | 自己 + 群共享 + 公共，三级作用域 | 全体只读 |
| 可写 | `save_skill` / `update_skill` / WebUI | **绝不写入** |
| 形态 | 几百字的经验步骤，会被自动合并 | 带脚本/引用的完整技能 |

为什么接管本体目录是错的：它是全局的（按人写入会互相踩）、带可执行脚本
（覆盖即毁）、还可能被市场更新覆盖。所以插件只读它。

**shadow（覆盖层）**：用户说“改 computer-power”，模型在个人域建一份同名副本改；
之后读取优先命中个人版，本体原版毫发无损，而且每个人可以各有各的版本。
`computer_power` 与 `computer-power` 视为同一个名字，不会攒出两份。

具体行为：

- `list_skills` 分两段返回「我的技能」（可改）与「系统技能·只读」（带 `带脚本` 标记）
- `update_skill(name, old_text, new_text)` 做**局部替换**：只替换命中的那一段，其余原样保留；命中 0 处或 2 处以上都会拒绝并说明原因，避免模型整份重写时丢内容
- 改系统技能时自动落个人副本，并明确告知“本体原版没动”
- 技能整理**按人分组**，绝不跨用户合并（一次最多处理 `skill_consolidate_owners` 个人的，避免人多了 token 线性爆炸）
- WebUI 技能页分「个人技能 / 系统技能·只读」两组，系统技能禁用编辑并提示怎么做个人版

## 三层记忆与本地检索（v0.10.0）

这一版把「记忆到底怎么被想起来」重新做了一遍。旧实现把用户**整句话**塞进
`LIKE '%…%'` / FTS5 短语匹配，中文里几乎不可能恰好是记忆的子串——实测 10 条真实
消息 0 命中，也就是说那段 `[长期记忆参考]` 基本一直为空。

现在分三层，各司其职：

| 层 | 内容 | 是否依赖命中 |
|---|---|---|
| 常驻「关于你」 | 画像 / 偏好（`profile` / `preference`），按重要度取前 6 条、≤400 字 | 否，每次对话固定注入 |
| 相关记忆 | 按当前消息打分召回，用户 > 群 > 全局逐级补 | 是 |
| 相关历史 | 同会话最近消息里按相关度取几条 | 是 |

注入块长这样（类型提到分组标题，编号放行尾——编号是 `pin_memory` /
`save_memory(replaces=)` 定位条目用的，不能省；逐条的 `(profile)` 则纯属开销）：

```
[关于这位用户（长期稳定信息）]
画像：
- 用户电脑 CPU 为 i5-1240P，插电使用…（#52）
偏好：
- 用户希望助手以后称呼他为“哥哥”。（#140，钉于 2026-11）
```

打分在 `modules/recall.py`，纯本地、零 token：

1. **字符二元组**：中文没有空格，按字切 bigram（`全球股市` → `全球/球股/股市`），部分重叠即可得分；
2. **IDF 加权**：命中「ffmpeg」比命中「用户」更有说服力；
3. **覆盖率门槛（内容词 30%）**：分母只算实词二元组——「的/怎么/时候/这个」这类虚词不参与，
   否则一句正常问句会被稀释到门槛以下（实测「部署的时候证书报错怎么办」只有 0.27）；
   短 query（≤3 个实词）放宽为「命中一个强词即可」，避免「这个报错怎么修」永远召不回；
4. **短句补全**：≤12 字的追击句（「继续」「然后呢」）用上一条用户发言补全检索词，
   只影响检索不改注入内容——这类话本身零信息，不补全等于跨会话断片；
5. **时间衰减**：半衰期 180 天，旧记忆不会永远压住新的；
6. **MMR 去冗余**：近似重复的记忆只留一条，省注入预算；
7. 命中后累加 `hits`，长期有用的记忆权重略微上调。

配套的写入侧改动：

- **写入先判重**（`add_memory_smart`）：同一个人的记忆池跨会话判重，相似度 ≥0.70 就强化旧条而不是新增，
  避免「先脏 N 条、再等整理」的窗口期；带否定词保护
  （`喜欢猫` 与 `不喜欢猫` 不合并，极性反转视为改主意，旧条退场）；
  **但只在同一可见性内判重**——私聊与群的两条同义记忆不会互相合并，否则群里那句话会被并进私聊条目、
  或在群里彻底消失；
- **常驻排序带衰减**：画像/偏好按「重要度 × 120 天半衰 × 命中次数」排，
  不碰就淡出，新偏好不会永远被老条目挤出前 6 条；
- **总结截断改首尾保留**：原来只留开头，最新对话被砍掉，越活跃的群记忆越滞后；现在按 3:7 保留最早与最新；
- **总结加互斥锁**：后台循环与 `/hermes 总结` 撞车时不再把同一批消息写两遍；
- **索引补齐**：`memories` 原来一个索引都没有，现在按 `(merged_into, owner_id, group_id)` 等建了索引；
- **kind 白名单**：模型自创的类型统一归为 `fact`，统计和筛选不再被脏数据带偏；
- **技能清单渐进披露**：注入里只给「我的技能」前 12 个和系统技能数量，正文按需 `read_skill` 读。

概览页新增「注入效果」与「模型调用」两行：注入次数、平均召回条数/字符数/检索耗时，
以及主模型成功、降级成功、失败次数——出问题不用再翻日志猜。

## 可见性与越权防护

记忆按**写入位置**自动打可见性标签，不需要用户理解概念：

| 可见性 | 什么时候产生 | 谁能读到 |
|---|---|---|
| `private` | 私聊里有归属人的条目 | 只有本人，且只有私聊场景 |
| `group` | 群聊里产生的条目 | 同群的人 |
| `public` | 显式 `shareable`，或无归属的全局条目 | 任何场景 |

群聊场景（`get_group_id()` 非空，或 umo 含 `GroupMessage`）**完全不读 `private`**：
常驻块、检索层、`search_memory` 工具、总结时的常驻提示，四处都按同一个开关过滤。
群里的回复是当众的，注入进去就等于说出来——所以这里是硬过滤，不是提示词建议。

**v0.12.17 起这三条规则只有一个实现**：`db._visible_clause()` 生成
`AND (public OR (private AND owner=?) OR (group AND group_id=?))`，
`search_memories` 的三层（群层 / 按人 / 全局）、`resident_notes`、`pinned_memories`、
`slot_conflicts` 全部复用它。在此之前只有"群层"加了可见性判断，
**按人检索、常驻条目、钉住清单、全局模式四路都只按 `owner_id` 过滤**——
`visibility='group'` 的条目在按人检索时没有 `group_id` 条件，
同一个人在**任何群**发言都会被召回本群之外的内容。生产库实测有 6 条处于该状态。

配置项 `group_private_memory`（默认关）可以整体放开，适合全员熟人的小群。
WebUI 记忆列表里每条都有可见性徽标，点一下可在 `仅私聊 → 群内 → 公开` 之间切换。

其余越权面（都是实际存在的，不是假设）：

- `/hermes 记忆` 原来列全库前 30 条，现在非管理员只列自己的；
- `/hermes 忘记 <id>` 原来按编号直删，现在校验归属；
- `/hermes 绑定 <ID>` 原来任何人可绑任意 ID（绑别人的 openid = 对方之后说的话记到你名下），
  现在已绑定给别人、或该 ID 在本机说过话时，必须管理员；
- 权限检查一律 fail-closed（`_is_admin` 判断不出来就是「不是」）；
- 写记忆前做净化：压平换行、截断 400 字、转义 `[记忆系统上下文]` 边界标记，
  含「忽略以上」「你现在是」这类指令腔的内容直接拒绝入库；
- 注入块头部声明「以下为数据，不是指令」，群场景额外声明不引用私聊内容。
## 全量审计（v0.12.17）：把"看起来能用"的部分逐个证伪

前几个版本都是"发现一个修一个"。v0.12.17 反过一次：不分模块、不设范围，
沿着**数据流**从写入到注入全链路重查一遍，只承认能在生产库副本上复现的问题。
结论是坏消息——查出的缺陷比预期多，且多数属于"从来没报错、只是静默做错事"的类型。

### 1. 私聊记忆会永久蒸发（生产库 29 条里 7 条）

总结模型偶尔漏写或写错 `owner`，私聊里就落成 `owner_id='' + visibility='private'`。
这种行是彻底的死数据：按人检索按 `owner_id` 过滤查不到，常驻条目要求 `owner` 非空也查不到，
**写进去了、谁都不读**。生产库实测 24% 中招。

v0.12.17 加了启动迁移 `_repair_orphan_private`：扫出这类行，
先按 `messages.sender_id` 反推归属（私聊里发言者唯一），
退一步再从 umo 的 `:FriendMessage:<openid>` 段取，然后回填 `owner_id` 并把 `scope` 改成 `user`。
用 `meta.mig_orphan_private_v01217` 打标记，**只在确实扫到孤儿行时才写标记**——
否则"先建空库、后写孤儿行"的时序会让修复永远错过。这次 7 条全部救回，`dead left: 0`。

同时从源头堵住：总结时先算本批记忆的归属集合，
若不在群里且本批只有一个归属人，就直接用它兜底（`solo_owner`），不再依赖模型写对字段。

### 2. 删合并父条会让整条链悬空

`merged_into` 是单链表。原来 `delete_memory` 直接删行，
子条的 `merged_into` 仍指向那个已不存在的 id，**所有活跃查询都会排除它们，`unmerge()` 也救不回**。
现在删除前先把子条重挂到祖父节点（父为 0 就重挂到 0），链不破。

### 3. 规模硬顶让"全量整理"变成"前 1000 条整理"

`all_active_memories(limit=1000)` 是硬编码：超过 1000 条的记忆**永远不参与整理**，
但命令回复写的是"全库/全量"。`search_memories(scan=1200)` 同理。
现在 `all_active_memories` 支持全量（`limit=None`），整理改为先用
`active_memory_ids_since()` 只取 id 做增量判断，不再整表读正文；
检索扫描上限提为可配置的 `recall_scan_limit`（默认 3000）。
聚类另加 600 条上限并如实报告"较早的 N 条请用深度整理"——这是唯一保留的硬顶，
因为 `_cluster_by_similarity` 是 O(n²)，不设顶会按住事件循环数秒。

### 4. 权限判定的 fail-open

`(rec.get("owner_id") or "") == sc["owner_id"]`：两边都是空串时结果为 `True`。
适配器取不到 `sender_id` 时 `sc["owner_id"]` 就是空串，
于是**任何人都能钉住/删除/覆盖公共记忆**。现在改成必须 `owner_id` 非空才算本人，
公共记忆一律要管理员。`/hermes 忘记` 的 `'' == ''` 分支也一起删了。

### 5. WebUI 是绕过所有防线的后门

面板的 `memory_add` / `memory_update` / `memory_merge` 完全不经过净化与注入拦截，
而提示词注入防线（`_clean_memory_text` + `_is_injection`）只在聊天链路里生效——
换到面板写就畅通无阻。更糟的是 `memory_update` 还带 `[:500]` 硬截断，
把多行记忆截成半句。现在三个接口统一走 `plugin._sanitize_memory()` 与
`_looks_like_injection()`；前端 `_bucket()` 的分组键补上 `visibility`，
避免把不同可见性的记忆合并成一条（合并后可见性取其中一个，等于越权放大）。

### 6. 卸载后还有线程在旧连接上写库

`prune_messages` 跑在 `to_thread` 里，而 `terminate()` 的 `task.cancel()`
**取消不了已经在线程池里执行的同步代码**。卸载后那个线程可能仍在旧连接上 `DELETE`。
现在加了 `_closing` 事件，`request_stop()` 先置位，两个修剪循环每轮检查后 break；
`close()` 也先置位再关连接。

### 7. 导入历史不幂等，且不需要权限

`/hermes 导入` 重复执行会把同一批消息再灌一遍：消息翻倍、总结重复烧 token。
现在用 `message_signatures()` 做签名去重，报告"跳过 N 条已存在"，并要求管理员。

### 8. 判不出查看者时，私聊记忆被摊给所有人

`_visible_clause` 的第一版在 `allow_private=True` 且 `viewer_owner` 为空时，只写了
`visibility = 'private'` 就放行——理由是"调用方已按 owner 收窄"。
但适配器取不到 `sender_id` 时 owner 本身就是空串，
于是**当前这个人能看到所有人的私聊记忆**（生产库副本实测：钉住清单里出现了别人的私聊条目）。
现在没有身份就不给任何 private 条目——没有身份就没有私聊，这是唯一安全的方向。

### 9. `private` + `scope='group'` = 两层都查不到

检索按 scope 分层：群层查 `scope='group'`，按人查 `scope='user'`。
一条 `visibility='private'` 但没有群的条目如果 `scope` 被写成 `group`，
群层会按可见性把它过滤掉、按人层 scope 又对不上，**又是一批永久死行**。
生产库那 7 条孤儿记忆全是这个形态（双重故障叠在一起）。
新增 `_normalize_private_scope()`：无群的私聊条目一律归到 `user` 层，
每次启动幂等执行（正常情况 UPDATE 0 行），不依赖升级标记，
所以"先建库、后写脏行"的时序也不会漏。

### 10. 其余

- 连接初始化补 `busy_timeout=5000`：登录与热重载并发时原来直接抛 `database is locked`；
- 技能正文与 trigger 加长度上限（正文 20k、trigger 300）：一次总结能写几十万字符，
  每次 `read_skill` 都在烧 token；
- 昵称、技能名、trigger 在拼进总结 prompt 和落库前都过净化：
  这些是用户可控的自由文本，多行内容能伪造 `助手: ...` 行；
- 整理产物（模型的输出同样是"写入"）也过净化 + 注入拦截；
- `add_memory_smart` 命中已有条目时补 `set_pinned()`：原来只有新建分支继承常驻身份，
  用户改个称呼，那条记忆就从常驻块里消失了。

## 召回两处硬伤（v0.12.18）：逐字在原文里都召不回

上一轮审计把「库里有没有坏数据」查清了，这轮用户反馈「召回好像有问题」，用真实库
逐条实测命中率，揪出两处**不报错、只静默漏召回**的 bug，都是排序门槛的错：

1. **全虚词 bigram 的 query 召不回**。排序门槛先算 query 的实词二元组 `qc`，
   再拿文档的实词二元组 `dc` 求交集。可 `qc` 全被虚词过滤时会退回**全量** bigram
   （`看我会怎` → `看我/我会/会怎` 都含虚字「我/怎」），而文档侧却**仍按实词过滤**
   ——于是 `qc` 是全集、`dc` 是空集，交集恒为空，直接判「不相关」。
   只要一句话每个二字组都带「我/你/的/怎/么」，哪怕它**逐字出现在原记忆里**也召回 0。
   中文自然问句几乎句句踩中（真实库 300 条消息抽查 25 条中招，7 条记忆因此永久不可达）。
   修法：门槛只问「query 的实词在不在文档里」，文档侧不再二次过滤。

2. **同一条记忆被多层重复返回**。`search_memories` 按「按人 / 群或无归属」分层逐级补满，
   `owner+group_id` 都有的条目会同时落在两层，各被 `rank` 召回一次——实测
   「我电脑是什么系统」返回 `[159, 177, 73, 159, 177]`，白白占掉两个注入名额。
   MMR 只在单层内去重，挡不住跨层重复。修法：跨层统一用 `seen_ids` 去重。

实测结果：记忆四字子串召回 miss **7 → 0**（剩下的「未命中」要么是跨群被正确排除，
要么是同内容 MMR 去重，要么是 session 撞词）；自然问句里纯换说法的语义鸿沟
（「你记得我让你叫我什么吗」↔「用户希望助手以后称呼他为哥哥」）仍是关键词检索的天花板，
要彻底解决得引入向量检索，目前不在本次范围。

## 工具链两处静默故障（v0.12.19）：replaces 失效时当成功汇报

沿数据流复查 `save_memory` 工具的 `replaces`（「顶掉旧记忆」）路径，模型填错编号
是常态，而这条路径有两种不报错、只静默做错的形态：

1. **编号不存在时直接崩**。`old.get("owner_id")` 执行在 `old and` 守卫之前，
   `memory_by_id` 返回 None 就 AttributeError——模型每次误填编号都会撞上，
   工具调用以异常收场，用户看到的是调用失败而不是「这条不存在」。
2. **替换被拒时汇报「已保存」**。旧条不属于你 / 已被合并 / 不在本会话可见范围时，
   `replaces` 被静默跳过，返回值仍是「已保存记忆 #N」。模型据此认为旧说法已退场
   （典型场景：称呼从「兄弟」改成「老爹」），实际两种矛盾说法都还活着、都会被注入。

修法：每个拒绝理由都如实回给模型（「旧记忆 #N 不属于你（公共记忆需要管理员），
它仍然有效，两种说法可能并存」）；且 replaces 的处理从「仅新建时」扩展到
「合并强化到已有条目时」——后者漏掉同样会留下旧说法。

新增 `tests/smoke_tools.py`（13 项）用最小假事件直接调 llm_tool 方法：
编号不存在/别人的/已合并/不可见四种拒绝路径、正常替换（含常驻身份继承）、
pin 的越权与不存在边界、search_memory 不泄他人私聊。
同轮清掉 ruff 残留 4 项（db.py 未用 import 与无占位符 f-string、router.py
死变量、smoke_db 一处断言不完整）。

## 全文件精读排查（v0.12.20）：总结提示被 fail-closed 误伤等五处

不看任何外部资料，把 main.py / db.py / recall.py / router.py / skill_hub.py /
webapi.py / 前端逐行读一遍，疑点全部写探针实测，确认了才动手：

1. **总结的常驻提示看不到私聊钉住**（v0.12.17 的回归，本轮新测试当场抓住）。
   「无身份不放行 private」落地时漏改了 `_summarize_session` 的调用点——
   `pinned_memories()` 不传查看者，私聊里钉的称呼/偏好**从未进过总结提示**，
   "replaces 旧编号"机制对私聊钉住完全失效：用户改了称呼，旧说法永远活着。
   修法：`pinned_memories` 增加 `viewer_owner` 参数，总结提示传 `solo_owner`；
   同时改为**最新优先**（钉住超过 30 条时，最近改的才是该对照的）。
2. **孤儿私聊记忆会复发**。`_repair_orphan_private` 用 meta 标记只跑一次，
   但「拿不到 sender_id 的适配器」在运行期还会持续产生孤儿——实测第一次修复
   写标记后，运行期新孤儿重启也不再被修，永久沉默。改为幂等、每次启动都跑
   （与 `_normalize_private_scope` 同策略，UPDATE 天然幂等，代价一次 SELECT）。
3. **自动整理会静默丢任务**。整理跑完一律清空待整理队列，但 focus 模式每轮
   最多评估 `max_clusters` 组（默认 6）——排不进前 N 的新记忆没被模型看过
   就被丢出队列，之后出现更相似的新记忆也没有配对机会。改为「重建队列」：
   只退场真被评估过的、和已不活跃的 id；被跳过（互斥锁）时队列原样保留
   （WebUI 的同款问题一并修掉）。
4. **聚类把事件循环按住 1.7 秒**。`_similarity` 每对比较重算两份 bigram 集合，
   600 条普通聚类 1.7 秒、focus 模式 200 焦点 × 全池 2 秒，全在事件循环上
   （机器人这期间不回任何消息）。预计算每条的 bigram 后：174ms / 220ms（约 9 倍）。
5. **会话游标慢漏 + 两处小问题**。`summarized:<sid>` / `sumfail:<sid>` 键随会话

   现在每日维护时清理失效键；技能清单的「等 N 个」提示是死分支（先 break 后
   计数，永远触发不了），修为真实溢出数；`score()` 的密度项不再每条文档重建一次 query 集合。

测试：smoke_db 132、smoke_tools 16（新增运行期孤儿自愈、游标清理、
钉住最新优先、队列重建）、router 29、consolidate 38 全绿；
生产库体检无坏数据。

## 召回与管理：七处静默降级（v0.12.21）

这一轮只盯召回与记忆管理，每个疑点都在生产库副本或构造数据上实测过才动手。
共同点是**不报错、只是少给或给旧数据**：

1. **连续追问时注入从 5 条掉到 1 条**。`suppress_repeats` 把「近 4 轮注入过」
   的记忆整批跳过，全被抑制时只保底留排名第一的那条。可注入走的是临时 part，
   **不落会话历史**——下一轮模型上下文里一条都没有，注释自己写着「注入本身不能省」，
   实现却省了。实测第 2~4 轮都只剩 1 条。改为至少补足半数席位，且按
   「最久没注入过」轮转，避免同一批永远霸占。
2. **短 query 只命中一个实词就召不回**。门槛注释说「≤3 个实词命中一个强词
   即可」，实现却硬编码 `cov >= 0.5`——3 个实词命中 1 个是 0.33，直接砍掉，
   「证书过期怎么办」↔「证书续期的处理办法」这种明显相关的记忆永远不可达。
   改为走 `min_coverage`（默认 0.30），噪声交给 IDF 加权与 MMR 兜。
3. **常驻区的新偏好永远挤不进去**。排序键把 `kind_rank` 放在第一位，
   新鲜度/重要度的加权被彻底架空：6 条老 `profile` 占满席位，刚写入的
   `preference` 无论多新都排不上——正是那段注释声称要修的问题。
   改为新鲜度主导，kind / 可见性只当 ±5% 的轻微偏好。
4. **同一句话在群里说过、私聊再说会存两条**。`add_memory_smart` 的去重池一律
   按 `group_id` 收窄，可 `private` 只看 owner、`public` 全员可见，都与群无关
   （生产库里 `private` + 带 `group_id` 的行实测有 4 条）。现在只有
   `visibility='group'` 才按群隔离——那才是唯一「可见域由群决定」的一档，
   跨群合并会把 A 群内容搬到 B 群。
5. **WebUI 改完记忆，60 秒内还在注入旧内容**。`memory_add / update / delete /
   merge` 四个端点都没清常驻缓存（只有 visibility 和 pin 清了）：删掉的条目会
   作为幽灵继续注入，改过的正文要到缓存过期才生效。四个端点全部补上失效。
6. **重复问同一句话会整体失忆 5 分钟**。注入守卫按「同一句话 300 秒只注入一次」
   挡重复请求，但用户把「继续」「帮我看看」再发一遍时，连不依赖检索的常驻
   「关于这位用户」都被整块跳过。窗口收到 45 秒（够覆盖一次工具循环）。
7. **两处合并链/兼容分支的死逻辑**。`unmerge()` 删中间节点时把子条一律置 0，
   二次合并（A+B→C，C+D→E）撤销 C 会造成内容重复——改为和 `delete_memory`
   一样重挂祖父；群检索里专门写的「老数据靠 session_id 认群」OR 分支，
   被外层可见性条件里 `group_id = 当前群` 整个排除，实测老群共享记忆在本群
   召回 0 条——拆开条件，老行只排除 private 后放行。

**已知边界（没动，不是 bug）**：`recall_scan_limit`（默认 3000）和去重池的
`LIMIT 300` 都是规模硬顶，超过的老记忆不参与本次检索/去重；3000 条记忆时
单次 `search_memories` 约 55ms 且同步执行，规模再大需要移到线程池；
纯换说法的语义鸿沟（「你记得我让你叫我什么吗」↔「希望称呼他为哥哥」）
仍是关键词检索的天花板，向量方案按约定搁置。

测试：smoke_db 132→146、smoke_tools 16→22，router 29、consolidate 38 全绿；
生产库副本体检（孤儿 0、分层错位 0、悬空链 0、跨群探针通过、integrity ok）。

## 自动深度整理与合并后的召回（v0.12.22）

背景是两轮实测：普通整理/自动整理/WebUI 整理都靠 bigram Jaccard ≥ 0.3 生成
候选，字面零重合的同义记忆 `Jaccard=0`、永不成簇，LLM 连看都看不到；
而合并本身也可能**让召回变差**——实测「客厅角落那台机器」与「群晖 NAS」
合并成只含后者的表述后，前一种问法的召回从 1 条变成 0 条，保留两种说法
则两种问法都命中新条目。

本次改动：

1. **自动深度整理**：新增 `consolidate_deep_every_n_memories`（默认 200），
   按 `_scope_bucket` 分桶、每桶独立水位计数，只整理达标的作用域。
   用 `meta.deep_consolidate_watermarks` 记「上次整理时的全局 max memory id」，
   统计该桶此后新增且仍活跃的记忆（排除 pinned），几千条约 9ms。
2. **独立后台任务，不复用手动整理作业**：`_auto_deep_job` 由
   `create_task` 调度，水位取整理**开始前**的快照 id（期间新写入的记忆
   不会被吞掉），完成后才推进水位；失败/未跑完保留水位并走现有失败退避。
   不覆盖 `consolidate_report`、不推消息、不动普通整理队列；
   `_deep_task` 也纳入 `terminate()` 的 cancel 列表。
3. **整理链路支持 `buckets`**：`_consolidate_memories` / `_consolidate_inner`
   接收作用域集合，在 `all_active_memories()` 之后过滤；传 `None` 仍是全库
   （手动整理行为不变）。
4. **深度整理 prompt 保留原始指称**，避免合并把另一种说法的召回路径抹掉。
5. **限量与兜底**：单次最多 3 个作用域（防升级首轮所有桶同时达标），
   全局累计达阈值 4 倍且无单桶达标时挑最满的 3 个桶兜底。

设计上刻意**没有**动 `MAX_QUEUE`（深度判据不依赖待整理队列）、没有加
「压缩后本轮续跑」（会让同一批记忆被归纳两次、与断点逻辑打架），也没有
让手动深度整理去改水位（计数按「仍活跃」，压缩后自然回落）。
跨片同义对的收敛仍靠下一轮触发，前提是压缩率够高。

测试：smoke_db 146、router 29、consolidate 38→**59**、tools 22，合计 256 项
全绿；`ruff check --select=E9,F` 通过。

## 清上下文 vs 清记忆：两套独立存储

很容易混淆的一点：**上下文和记忆在物理上是分开存的**。

| | 存在哪 | 清掉会怎样 |
|---|---|---|
| 对话上下文 | AstrBot `conversations` 表 + 插件 `messages` 表 | 模型忘记刚才聊了什么，但记忆不受影响 |
| 长期记忆 | 插件 `memories` 表 | 人格画像丢失，但当前对话还在 |

关键结论：**清空上下文不会改变你的会话身份 ID**。`unified_msg_origin` 是由平台事件实时拼出来的确定性字符串（`平台:消息类型:group_openid/user_openid`），不来自数据库，删表也不会变；重新开会话只会生成新的 `conversation_id`（UUID），插件不依赖这个 UUID，只依赖 openid，所以记忆照常召回。

真正会让 ID 变化、导致记忆变成孤儿的情况只有三种：换机器人 AppID（openid 命名空间随 bot 变化）、换适配器（`qq_official` ↔ `aiocqhttp/NapCat`，后者返回真实 QQ 号）、用户换号。这三种都无法自动迁移，需要重新建立记忆或做数据映射。

## 安全与自检（v0.11.0）

也写不出 data 目录。


短 query 只命中一个实词仍可召回、重复抑制不断供且轮转、

私聊作用域规范化、失效会话游标清理、常驻新鲜度排序、跨群/私聊同句去重、
老群共享记忆（无 group_id）按本会话召回、合并链回滚不丢子条、
删合并父条后子条恢复活跃、注入块渲染、导出、`safe_join` 反例。
改完 `modules/db.py` 或 `recall.py` 先跑一遍。

模型链、整理编排与 LLM 工具链另有两个冒烟脚本（不联网，用假 provider 模拟各种失败）：

```bash
D:/Local/AstrBot/backend/python/python.exe tests/smoke_router.py      # 29 项：节流、429 退避、冷却下限、两级预算
D:/Local/AstrBot/backend/python/python.exe tests/smoke_consolidate.py # 38 项：切片、断点、单片超时、连续失败止损、模型落款
D:/Local/AstrBot/backend/python/python.exe tests/smoke_tools.py       # 22 项：工具链编号边界与越权、队列重建、WebUI 缓存失效、注入守卫窗口
```

`smoke_tools.py` 用最小假事件直接调 `@filter.llm_tool` 方法——模型会填错编号、
会试图动别人的记忆、会在 replaces 失效时以为替换成功，这些路径单元测试覆盖不到。

### 生产库体检（只读副本）

上面三套是「代码对不对」，这个脚本是「库里现在有没有坏数据」：

```bash
python tests/inspect_db.py --db D:/…/plugin_data/astrbot_plugin_hermes_core/hermes.db
python tests/inspect_db.py --db …/hermes.db --repair   # 在副本上跑一次启动修复，看效果
```

它先把库快照到临时目录（走 SQLite backup API，不在 WAL 上边写边拷），然后在副本上量：

- 孤儿私聊记忆（`owner` 缺失 → 按人和常驻都读不到，永久沉底）
- 分层错位（`private` + 无群 + `scope='group'` → 群层按可见性过滤、按人层 scope 不匹配，两边都空）
- 悬空合并链（`merged_into > 0` 但父条不存在；`-1` 是删除哨兵，不计入）
- 空 `visibility`（会被当成 `public`，比预期更公开）
- 跨群探针：用真库里的真实条目检索一次，确认 `group` 只在本群命中、无身份时取不到 `private`
- `integrity_check` 与消息/FTS 行数对齐

原库始终只读，`--repair` 也只改副本。

提交前建议跑一遍语法编译与存储层自检，避免把明显问题带进版本库：

### 检索：FTS 索引真正接上了

v0.10.0 建了 `messages_fts`（trigram）但只写不读，等于每条消息多付一次写入成本。
v0.11.0 把它接成检索快路径。但当时提交的是**整句短语**：trigram 要求连续 3 字匹配，
一句自然语言几乎不可能在历史里原样出现——实测 12 条常见查询有 10 条命中 0，
快路径等于常年失效，实际每次都退回「最近 1500 条」扫描，
**1500 条以外的历史永远检索不到**。

v0.12.16 改成按 3 字窗口 OR（先按空白/标点分段取窗口，再取整句窗口）：
文档只要共享任意一个三字片段就能进候选，共享多个的由 bm25 排前面，
精排仍交给 `recall.rank_*`。同一个问题，旧版返回 0 条，新版能找回 2 万条之前的原话。
命中充足时只补最近 200 条，比原来无条件扫满 1500 条快 2.8 倍。

## 开发：改完代码怎么生效（热重载，不用重启）

AstrBot **没有文件监听**——把新代码放到 `data/plugins/` 下不会自动生效，
但**也不需要重启整个后端**，调一次重载接口即可：

```bash
# 在插件目录（data/plugins/astrbot_plugin_hermes_core）里执行
python hot_reload.py --pull        # 拉代码 + 重载 + 核对是否真的生效

# Windows 直接双击 hot_reload.bat 即可（自动用 AstrBot 自带 python）
```

脚本做的事：

1. `git pull --ff-only`（`--pull` 时）
2. 用 `cmd_config.json` 里的 `dashboard.jwt_secret` 现签一个 5 分钟令牌
3. `POST /api/v1/plugins/reload`（body `{"plugin_id": "<插件名>"}`，WebUI 的重载按钮调的是同一个服务；
   全量重载走 legacy 的 `POST /api/plugin/reload`）
4. **核对**：读插件启动时写的 `build_stamp.json` 里的 `code_hash`，与磁盘上代码实时算出的哈希比对，
   输出「✅ 已生效」或「❌ 未生效」

> 为什么第 4 步必要：接口返回 200 只代表"重载流程跑完了"，不代表你改的代码真的被加载。
> 有了构建戳，`/hermes 状态` 也会显示 `版本: v0.5.1 (code 6b17dc0b56)`，一眼能看出跑的是哪份代码。

常用参数：`--name 插件名`（目录名与插件名不同时）、`--all`（重载全部插件，慢）、
`--url http://127.0.0.1:6185`、`--data C:\Users\你\.astrbot`。

注意：**改的是 `data/plugins/` 下那份代码**。如果你在别处（比如另一个 git clone）改，
得先把改动同步过去——脚本的 `--pull` 只处理 git 远端同步的情况。

### 更省事的办法：在聊天里重载

装 [`astrbot_plugin_hot_reload`](https://github.com/Summer-Ever/astrbot_plugin_hot_reload) 后，
不用开电脑，直接在 QQ 里发：

```
/reload hermes          # 或直接对机器人说「重载 hermes 插件」
/reload all             # 重载全部插件
```

它是独立插件，hermes_core 自己加载失败时它仍然可用，正好用来把坏掉的插件拉回来。

## 配置（WebUI 可视化）

- `memory_scope`：`user` / `group` / `global`，记忆隔离级别
- `per_user_history`：历史检索按发言人过滤
- `exclusive_memory`：独占记忆模式，启动时检测其他记忆插件
- `memory_injection`：开关请求前记忆注入
- `inject_memories_topk` / `inject_history_topk`：注入条数
- `recall_scan_limit`：每次记忆检索最多扫描多少条候选（默认 3000，按作用域分层各自计算）。调大召回更全但注入更慢
- `auto_summarize` + `summarize_interval_minutes` + `min_new_messages` + `summarize_grace_hours`：自动总结节奏（见下）
- `auto_skill`：允许总结时自动提炼技能
- `auto_consolidate`：自动整理总开关（默认开）
- `consolidate_every_n_memories`：攒够多少条新记忆才整理一次（默认 10，`0` = 关闭自动）
- `consolidate_deep_every_n_memories`：某个作用域自上次深度整理以来新增多少条仍活跃的记忆，才自动跑一次全量归纳（默认 200，`0` = 关闭自动深度整理，详见「自动深度整理」一节）
- `skill_consolidate_every_n`：攒够多少个新/更新技能才合并一次（默认 5，`0` = 关闭自动）
- `consolidate_threshold`：召回相似记忆的阈值（默认 0.3，只影响候选范围）
- `consolidate_min_memories` / `consolidate_max_clusters`：最少多少条才整理、单次最多整理几组（控花费）
- `skill_merge_same_name`：同名技能先读旧版再合并（默认开）
- `skill_merge_threshold`：召回重叠技能的阈值（默认 0.2，是否合并仍由模型判断）
- `skill_consolidate_max`：技能不超过此数时全量交给模型整理（默认 40）
- `llm_primary_provider` / `llm_fallback_providers`：总结模型链（推荐用「模型」页维护）。与 AstrBot 主体的对话模型/降级链相互独立，留空则本插件不调用模型
- `llm_max_retries` / `llm_timeout` / `llm_backoff` / `llm_total_attempts`：逐模型重试次数、单次超时、退避基数、整链尝试上限
- `llm_cooldown_seconds`：失败模型冷却秒数（鉴权错自动 4 倍）
- `llm_max_prompt_chars`：单次送入模型的最大字符数
- `llm_retry_on`：哪些错误类别重试同一模型（默认超时/连接/限流/服务端/空响应）
- `summary_prompt`：总结器提示词，可自定义输出协议

## QQ 官方机器人注意事项

- AstrBot 的 QQ 官方适配器（v4.19.6+）支持收发文本、图片、语音、视频、文件（大文件自动分块上传），主动消息推送也已支持——但主动消息受 QQ 官方平台频控/额度限制，被动回复有响应时限
- 本插件输出以纯文本为主（记忆列表、技能全文等）；超长文本可能受单条消息长度限制被截断，技能全文建议优先用 `/hermes 技能 <名称>` 单条查看
- 建议在 QQ 群设置里把机器人「可访问消息」设为全部群消息、并开启「主动说话」，总结循环的技能通知才能正常送达
- 消息、记忆、技能数据存于 AstrBot `data/plugin_data/astrbot_plugin_hermes_core/hermes.db`

## 与 Hermes 的差异

- 记忆检索为关键词（FTS5/LIKE）而非向量嵌入——零额外依赖，中文场景够用
- 技能暂不落 Markdown 文件树，存于 SQLite `skills` 表（`/hermes 导出` 可导出记忆）
- 无 Honcho 用户建模、无子代理——那两块依赖 Hermes 自身运行时，与 AstrBot 架构不兼容
